# A2Game 三款完整游戏业务验收方案

**初版：2026-11-22｜修订：2026-11-23｜版本：1.1 业务验收设计｜实施状态：作者版桌面与离线交付通过，独立 Agent 和真机待验。**

三款作者版及独立包已构建。当前回执、未通过项和待跑项目见 [项目进展](../../PROJECT-STATUS.md) 及 [状态台账](../../project/status.json) 的 `threeCompleteGamesBusinessRun`。下文的用例状态保留设计基线。

**结论：可行。以经典微信打飞机、羊了个羊、开心消消乐为玩法参考，构建三款可以从入口独立游玩、完整结束、重试并保存必要进度的作品，用它们验收“Agent → JSON → 共享 Runtime → 真实播放器 → 交付包”整条链路。**

初版评估基线为 `13c64dc`；本次复核使用本地 `bab35b3b3422f5eb8adef02b4cdc4db7d00daee2`，包含 v2 原型交付、Generator 入口迁移和 Player SDK 的 `RenderSetup` 接口。实施开始和交付取证时各记录实际提交与相关工作区差异。

三款作品采用原创名称、素材、界面与关卡，参考产品用于选取通用玩法机制。三款业务验收与现有 84 款的逐款复审是两个任务。沿用本方案的关卡、续玩和交互检查维度逐款建立缺口清单，三款通过后仍须逐款登记其余作品的结果。

## 1. 三款作品怎样共同验收 A2Game

| 业务场景 | 参考游戏 | 主要验证对象 | 与旧目录的关系 |
|---|---|---|---|
| BIZ-01 | 经典微信打飞机 | 连续输入、固定时钟、生成回收、弹丸伤害、碰撞、持续得分、性能 | 扩展G17的完整作品；不自动升级G17正式状态 |
| BIZ-02 | 羊了个羊经典叠牌玩法 | 遮挡拓扑、牌身份、受限槽位、原子操作、道具、可达解、持久恢复 | 扩展G04的完整作品；不自动升级G04正式状态 |
| BIZ-03 | 开心消消乐经典交换消除 | 特殊块、障碍、匹配优先级、连锁、目标步数、关卡进度、表现时序 | 扩展G03；H02等可后续复用，不算本轮已验 |

两个消除游戏的算法和交互差异很大：BIZ-02选择的是具有遮挡关系的独立牌，BIZ-03操作的是相邻棋盘格并触发下落/连锁，不能用同一简单消除演示换皮交付。三款通过后，可证明最初“益智、休闲、射击”主线具备完整作品级链路；不能据此宣称RPG、3D、音乐、联网、UGC或224项目标全部完成。

## 2. “真正完整”在本轮的含义

每款都必须交付以下内容：玩家入口与必要教学、实际可操作的主要循环、清楚的目标/反馈、胜败或得分结算、重试与返回、设置、暂停恢复、必要的本地进度、完整图像与音频资源、公开内容入口和可独立启动的包。正式页面中不能要求玩家手填JSON路径、使用调试按钮、手动推进Tick或注入获胜状态。

本轮将完整性拆成四个可核对结论：

| 结论 | 通过需要什么 | 当前状态 |
|---|---|---|
| 功能Profile完整 | 本文已冻结规则和内容要求全部可执行，必需业务用例通过 | NOT_RUN |
| 参考规则/手感相符 | 锁定具体原版平台、版本、模式和操作证据，逐项校准差异 | REFERENCE_CAPTURE_PENDING |
| Agent可生成 | 新上下文基于公开能力/资源生成完整内容及未见变体，通过同样检查 | NOT_RUN |
| 微信服务接通 | 若纳入账号/榜单/广告等范围，必须有对应真实服务证据 | NOT_IN_CORE_PROFILE |

本轮完整作品以明确、可制作的经典核心玩法范围为准。官方产品长期积累的全部关卡、活动、商业化和社交生态是另外的服务范围；本轮不会将本地最高分、固定道具库存或模拟服务写成微信服务已接通。

### 2.1 参考资料与设计选择

资料分为 `official-description`（官方描述）、`observed-reference`（固定原版实测）、`designed-profile`（本轮设计选择）、`unconfirmed`（未确认）。原版参数不足时，先用本文明确给出的设计Profile实现完整作品，原版一致性状态保持待核对；不能用“全部待定”替代设计，也不能把设计数值冒充原版数据。

- [简游官方产品页](https://easygame2021.com/index.php?a=index&c=Lists&m=home&tid=4)确认羊了个羊的消除闯关定位；[官方商店页](https://apps.apple.com/cn/app/%E7%BE%8A%E4%BA%86%E4%B8%AA%E7%BE%8A-%E6%98%9F%E7%90%83/id1644374326)当前为《羊了个羊：星球》，新增玩法不能直接混入经典版。
- [乐元素App Store开发者说明](https://apps.apple.com/cn/app/%E5%BC%80%E5%BF%83%E6%B6%88%E6%B6%88%E4%B9%90/id791532221)确认横竖同色至少3个消除、按指定目标过关；[官方魔力鸟活动说明](https://www.taptap.cn/moment/317353022915086154)确认相关交换消除机制存在，不足以推出完整特殊组合参数。

`reference-lock`应记录参考名称、平台、版本/日期、模式、证据位置、规则来源和未知项；它可包含未知项。只有声明“原版一致性通过”时，对应必需规则和手感的未知项才必须清零。这里的lock是建议实施的数据文档，不是当前已存在的工具或已完成的证据。

## 4. JSON、Runtime、宿主和Agent的职责

| 层 | 应负责 | 必须避免 |
|---|---|---|
| 游戏内容JSON | 规则参数、对象/棋子模板、关卡、目标、难度、输入绑定、流程、资源引用、表现映射 | 写入任意可执行脚本，调用未实现的字段来假装有功能 |
| 可信共享能力 | 生成、碰撞、消除、特殊效果、状态事务、随机数、目标、存档与流程语义 | 每款游戏单独藏一份规则代码，或直接按gameId跳到专用实现 |
| CocosAirJS / Three.js适配器 | 投影状态、播放表现/音频、桥接输入、管理原生资源 | 决定得分、胜败、遮挡可选性、特殊块生成或连锁结果 |
| 通用宿主服务 | 公共加载、资源准入、持久存储、通用关卡流转、生命周期 | 借助某款专用HTML/JS偷偷补上JSON未表达的玩法 |
| Agent | 理解规则、查询实际能力、选资源、生成JSON、运行检查、修复内容 | 编造能力、改Runtime替自己的输出过关、伪造试玩结果 |

统一从一个玩家入口启动。优先复用现有内容包和发布清单，为多关作品确定版本化目录，冻结作品 ID、关卡 ID 与顺序、关卡定义定位及摘要、资源摘要和所需协议/能力版本。实施前用两份最小关卡验证整包准入、切换和坏摘要拒绝；若现有格式不足，通过通用目录扩展。每份 GameSpec 从现有准入入口加载，游戏逻辑仍由共享 Runtime 执行。宿主根据已提交的终局结果显示下一关、重试或返回地图，切换前释放旧会话及输入。适配器沿用 `RenderSetup` 初始化并消费 `PresentationFrame`。

阶段 0 的参考实现采用 `a2game-game-collection` 版本 2。目录中的 `levels` 按游玩顺序排列，每关使用唯一 `id`、相对 `game` 路径和原始文件 `sha256`，以及现有参考界面需要的 `title`、`hint`、`par`。服务先核对全部关卡摘要，再调用现有内容准入。参考页当前按关卡发布摘要序列隔离完成记录。独立包的关卡目录、正式资源和各作品存档继续按下表实施。

| 作品 | 保存时机与恢复范围 |
|---|---|
| BIZ-01 | 终局提交时更新最高分，设置变更时保存。重新进入可开新局，长局不要求中途恢复。 |
| BIZ-02 | 每次有效选牌、消除或道具事务完整提交后保存。恢复棋盘、槽位、保留区、工具额度、随机状态与可撤回事务。 |
| BIZ-03 | 成功结算时保存解锁、最佳分和星级，设置变更时保存。重新进入从已解锁关卡继续，本轮不要求恢复局内棋盘。 |

保存记录绑定作品/关卡稳定 ID 与内容版本或摘要。同一交付入口重开或刷新后应可恢复；独立包更换地址或端口时不假定浏览器存储会共享。结算重复提交保持幂等；内容不兼容时保留旧记录并给出重新开始选项。现有 Replay Save 限制为 4,096 个事件、3,600 Tick；个人进度直接使用版本化记录。叠牌先用完整规模流程验证回放容量，必要时设计经完整状态校验的可信检查点，禁止向 Runtime 直接反序列化任意快照。

计分局新增 `score-session` 验收方式。证据须包含真实输入、预期分数与可核对的正常死亡结算，并验证重开隔离，无需构造获胜。叠牌和有限关卡使用 `finite-goal`，验证从正式初态达成目标及关键失败路径。这两项是验收工具的设计名称，现有 GameSpec 的字段和有限目标检查继续保留。

### 4.1 连锁、动画和输入

不强迫把三消逻辑跟着每一帧动画执行。可在一次事务中算完结果并输出完整有序结算事件与动画计划，也可使用确定性的分阶段逻辑。无论采用哪种方式，接收输入的时机、暂停恢复、结果提交和重复触发处理都必须由共享会话规定；不能让两种渲染器各自按动画回调改变规则。

### 4.2 当前源码事实的更正与新增关注

- **拖动已有实现基础。** [input-control.ts](https://github.com/oahc09/a2game/blob/13c64dc07c0e6dde3816f100216bad9565bb1ed0/src/modules/input-control.ts)有`moveMode=drag`、坐标转换和`moveClipped`。前一轮“未接到角色”的判断过重，本轮纠正为需按作品校准和验证完整触控语义。
- **叠牌已有规则基础但样例很小。** [G04](https://github.com/oahc09/a2game/blob/13c64dc07c0e6dde3816f100216bad9565bb1ed0/specs/v0.1/games/g04-candidate.game.json)是6张牌、4槽；容量变体为3槽。源码默认容量7不代表完整羊了个羊已经交付。
- **三消基础可复用。** [puzzle.ts](https://github.com/oahc09/a2game/blob/13c64dc07c0e6dde3816f100216bad9565bb1ed0/src/modules/puzzle.ts)已有普通交换/匹配/补落与有界连锁；需要补特殊块、障碍/目标、死盘处理、完整事件与作品流程。
- **同主人多弹命中是待实测风险。** [realtime.ts](https://github.com/oahc09/a2game/blob/13c64dc07c0e6dde3816f100216bad9565bb1ed0/src/modules/realtime.ts)按target+source去重且子弹传owner；SHT-08检查同玩家不同子弹同Tick是否分别造成伤害。本轮只有源码推断，没有写成已复现故障。

## 5. 如何形成可执行的业务测试

本包提供业务用例计划；不是当前Runtime可直接执行的GameSpec或测试脚本。每条用例记录前置、动作、精确预期、验证层、证据和`NOT_RUN`状态。执行前需要把计划中的夹具制作成有效内容与输入文件。

每个正式关卡/夹具应交付：

1. 内容版本和实际JSON；固定seed或明确的补充序列策略。
2. 从真实初态开始的规范化输入；必要时提供经过准入的边界状态夹具。
3. 独立写出的关键预期，例如分数增量、槽位、命中集合、剩余步数；不能直接拿待测代码本次输出当标准答案。
4. 可达解/得分路径与关键失败路径。解法由正式Runtime复验，不能用隐藏开关、修改随机数或加步数取代。
5. 同一内容在真实SDK下的可观察画面与输入证据。

### 5.1 可解性规则

羊了个羊：牌数可以被3整除不证明能过关；必须考虑遮挡、槽位和工具。开心消消乐：存在一个合法交换不证明能在步数内完成目标。固定正式关卡需要实际通关见证；未证实的随机种子不能凭概率宣称可解。

首轮优先制作明确可解的固定内容和已验证种子集合，再扩受约束生成。若洗牌/生成器承诺可解，需提供可达性验证或有证明的构造及Runtime复验。求解预算耗尽是`UNKNOWN`，不等于无解，也不能被登记为PASS。不能通过给玩家无限提示/自动解题移除原本的选择压力。

### 5.2 状态与表现分开核对

同一seed和规范化输入下，对比共享权威状态、重要事件和得分/终局；渲染对象ID、时间戳和GPU像素不混入玩法一致性Hash。与原版的随机局不能假定有相同内部seed；原版对照按冻结规则、可测参数、输入轨迹和体验证据进行。

界面须实际查看：羊了个羊遮挡和点击不能穿透，三消每个结算阶段可理解，飞机移动与碰撞可感知。截图、Headless、模拟触控和实际手机证据分别标注。

## 6. Agent创作验收：三款基础＋三款变体

平台开发者先完成通用能力与参考作品，用以验证工具链；随后在新的Agent上下文进行内容创作验收。公开上下文包含能力目录、规则Profile、资源ID、使用示例与诊断接口；不直接提供本任务作者JSON和通关答案。

| 任务 | 输出要求 | 验证目的 |
|---|---|---|
| AI-01/02/03 | 分别生成三款完整内容，满足本轮规模与流程 | 证明公开工具足以表达完整业务 |
| AI-04 | 改敌机配比/速度曲线/主题 | 证明飞机规则来自内容 |
| AI-05 | 改遮挡拓扑/牌分布 | 证明叠牌不是固定棋盘特判 |
| AI-06 | 新棋盘形状、障碍和双目标组合 | 证明三消机制可复用 |

变体生成时冻结Runtime与Adapter源码，只有内容/资源引用改变。若遇到真正缺失能力，应返回明确缺口，再按独立能力开发处理；不能一边改底层一边宣称“内容变体直接通过”。

允许正常的“生成→校验→试玩→修复”循环，记录首轮结果和最终结果。建议每任务最多3次输出尝试，但实际批次须使用已有授权预算，不复用已经耗尽的历史额度，不改变模型路由，不自动调用额外Provider。任务计划不等于新增真实调用授权。本轮仅设计，没有执行六项生成任务。

作者参考、Agent输出、宿主辅助求解、主审、独立复核、人工体验和真机结果分别记录。若人工编辑最终JSON，须如实记录，不能算独立Agent生成成功；模型声明“通过”不构成结果。

## 7. 运行范围与质量标准

优先复用既有Schema/Conformance、实际SDK输入回放、包验证工具。每个机制先做必要边界，再在完整游戏里走业务路径；同一段执行证据可支撑多条用例，不要求为每条用例另造脚本或重跑整个矩阵。

| 检查层 | 必需范围 | 不得替代的部分 |
|---|---|---|
| 规则和内容 | 所有正式关卡、关键正反例、固定seed复验、变体 | 不代替视觉、触控或正式包 |
| 真实双后端 | 每款一条完整正常路径和失败/重开路径；机制覆盖关卡在两端观察 | Mock/Canvas2D不计真实SDK |
| 真机触控 | 至少一台声明的目标Android设备，先验主交付后端；其他平台未测明确标注 | CDP触摸不计真机；不能外推iOS或其他宿主 |
| 打飞机长局 | CocosAirJS正常时钟30分钟，Three正常时钟10分钟；复用前10分钟输入；达到全部难度阶段 | 快速Headless不计真实时长，自动输入不计人工手感 |
| 持久与交付 | 三款独立包、干净启动、必要进度恢复、资源完整与失败诊断 | 预览页成功不计最终交付成功 |

### 3. 本轮冻结的规则合同

#### 分层与选牌

每张牌有稳定ID、图案、位置、层级和遮挡关系。遮挡关系必须无环，与视觉叠放吻合。只有仍在棋盘上且没有存活遮挡者的牌可选；同一手势只选择最上层一个合法目标，不能穿透下层。非法点击不记步、不消耗道具、不消耗RNG、不产生新的撤销点。

一次选牌事务：移出源区域→插入槽→同类归组→消除三张→检查失败/胜利。新牌插在槽内最后一张同类之后，没有同类则追加。第七张如果形成三消，应先消除再判满。例如槽为`[A,A,B,C,D,E]`时选择A，结果为`[B,C,D,E]`而不是失败。归组与消除是确定规则，不能依赖动画何时回调。

本Profile在结算/过场动画期间拒绝新的选牌输入并给予轻提示；动画结束后解锁。逻辑事务在固定Tick提交，减少动效不改变规则。涉及同时输入时由标准化序号确定顺序，记录拒绝原因。

#### 道具：每局各1次，精确行为属于本轮约定

- **移出**：仅在槽至少3张且保留区为空时可用；将槽最左侧3张按原序移到3格保留区，不消除、不加消除数。保留区中的每张牌仍须重新进入槽参与三消。保持牌ID和多重集守恒。
- **撤回**：只撤最近一次选择事务，包括该次触发的三消，恢复棋盘/槽/保留区/步数/消除数、可选集合和对应RNG状态。撤回道具自身消耗保存在不可被该次撤销恢复的域中。洗牌或移出后建立事务边界，不能跨边界撤销复制牌或返还工具。
- **洗牌**：只重排棋盘未取走牌的图案，不动位置、遮挡图、槽和保留区，保持棋盘牌面多重集。若宣称洗牌结果可解，需从当前完整状态验证实际可达解；不能只检查计数或可点击牌。候选求解预算用尽记为UNKNOWN，不等同证明无解；没有验证成功的候选就保留原状态且不扣额度。

每次事务满足：同一牌ID只存在一处；每类图案在棋盘+槽+保留区+已消除账本中的总量不变；额度不为负；胜负与进度不重复结算。撤销改变当前账本，但不能撤销已经提交的外部奖励。

#### 保存与恢复

至少保存内容摘要/规则版本、关卡ID/seed、全部牌的稳定ID/图案/区域、槽与保留区顺序、道具额度、RNG、步数及允许的最近撤回事务。只在事务边界落盘；动画中退出恢复到已提交事务并重建展示，不重复消除/奖励。版本不匹配明确诊断或执行受支持迁移，不能静默套用。

| 遮挡 | `puzzle.ts` 配置校验支持 `blockers` 无环图；`freeCell` 阻止被挡牌 | 与真实叠放视觉、稳定牌ID、命中层级统一；现有网格展示不能直接当层叠成品 |
| 槽与三消 | `tray` 分支push数值，达到matchLength消除，之后判槽满 | 稳定牌身份、明确同类归组展示、事务事件、保留区/道具和完整产品流程 |
| 胜负 | board清空且tray空获胜；容量默认7可配置 | 加入保留区清空；局内与产品结算一致 |
| 撤销 | 最多16个快照，恢复puzzle与RNG | 道具额度和原子事务边界；组合多个behavior时现有undo会拒绝准入，需明确修复路径 |
| 正式样例 | `g04-candidate` / `puzzle-tray`仅6张牌，capacity=4；变体capacity=3 | 不能当7槽、144牌、完整道具和产品流程已支持的证据 |
| 洗牌/移出 | tray公共Schema没有相应命令/配置；commands为空 | 新增可信机制，不以任意JS或gameId特判实现 |
| 可解性 | 样例有有限conformance场景 | 完整布局解路径、无法求解/证明无解区分、生成和洗牌的验证 |

### 4. 拟定完整产品内容

#### 玩家路径

### 5. 为了精确测试，先冻结的拟定规则

以下均为参考作品合同。若要求逐项原版一致，应以固定版本录屏/实测校正后修改，然后固定合同和夹具摘要。

1. 只允许正交相邻的可移动格交换。普通块必须形成匹配，或命中已声明的特殊组合条件；否则回弹，步数、棋盘、目标、得分、RNG 不变。
2. 每个被接受的玩家交换消耗 1 步；由此引发的特效、下落补充和连锁不再耗步。
3. 同色直线至少 3 个可消除。着色直线/爆炸特殊块具有颜色，参与普通同色匹配；颜色清除块无颜色，不参与普通颜色连线。直线恰好 4 个产生朝匹配方向的直线特效；5 个以上直线产生颜色清除块；至少 5 格组成 T/L 产生爆炸块。重叠优先级为颜色清除＞爆炸＞直线；先合并相交匹配，同一匹配分量最多生成一个特殊块。
4. 生成候选格必须是该匹配分量中的普通棋子格，不能选已有特殊块、已经为组合消费的格或别的生成计划占用格。玩家交换依次选择交换目标格、源格、行优先最小候选格；自动连锁使用行优先最小候选格。没有候选格就不生成新特殊块，已有特殊块仍按MR05激活。选定普通棋子转化为一个新ID的特殊块，旧普通棋子的退休是转化，不记清除分或收集目标；一个旧ID最多转化一次，同格同波最多一个生成物。**新生成特殊块在创建波内受保护**：本波匹配与其他效果都不再消耗或激活它；下一波及以后可以正常匹配/受击。生成规则不保护其底层障碍，底层仍按MR07最多扣一层。
5. 普通匹配含有已有特殊块，或特效命中另一已有特殊块，都将其加入激活队列；每个实例ID在同一玩家动作及其全部连锁中最多激活一次。入队时立即标记已消费，使用消费前的位置/颜色/类型生成效果，不再参加其他匹配或下落；可见删除在清除提交阶段完成。队列递归处理后续命中，重复命中只记录来源，不重复激活、删除、得分或收集。直线单独激活清除其朝向的整行/列；爆炸单独激活作用于中心3×3可用格；颜色清除块与颜色c普通块交换，消费两块并清除颜色c全部棋子。颜色清除块被其他效果命中且无配对颜色时，取本波开始快照中数量最多的可消除着色棋子颜色，并列取最小颜色ID，空集合则只消费自身。所有效果按稳定队列顺序和唯一棋子ID/事件ID去重；新生成物受MR04本波保护。
6. 六种特殊组合必须公开精确足迹：直线＋直线为目标格所在行列；直线＋爆炸为目标格中心3行与3列并集；爆炸＋爆炸为目标格中心5×5；颜色清除＋直线/爆炸将配对块颜色的棋子转换后按稳定ID顺序激活；双颜色清除作用于所有可用格。**识别组合后先消费配对的两个特殊实例并登记一次组合事件，只执行组合规则，不再叠加两块的单体效果，也不再按普通交换生成特殊块。** 组合击中其他特殊块，仍按MR05链式触发。颜色转换保留原实例ID、不计转化得分；同色已有着色特殊块可被覆盖为组合指定类型，旧类型不另触发；已消费或本波受保护实例不转换。颜色清除＋直线的新直线朝向统一继承配对直线，转换和激活顺序写入JSON合同，不能由画面帧率决定。
7. 冰为底层障碍：该格棋子被清除或受到有效特效时，每个结算波最多扣一层。箱体占格：邻接普通消除或有效特效每波最多伤害一次；本参考作品中直线特效穿过并伤害箱体，箱体只阻挡交换、占格和下落。若冻结原版要求不同传播规则，改规则表及足迹夹具，不在测试中模糊判定。
8. 所有匹配/特效/掉落/补充结束、棋盘稳定后，再判所有目标是否完成；最后一步完成目标判胜优先于零步判负。
9. 无合法交换且目标未完成、仍有剩余步数时，进行有预算的确定性洗牌，最多 64 次候选；保留棋子多重集、障碍、目标、步数和道具库存，不允许洗牌直接得分或完成目标。每次候选需稳定且有合法步；失败则进入带原因的死局结束界面，不挂起。不宣称“有合法步”就必然能通关。
10. 额外道具为本参考作品明确范围：锤子（对选定格作一次有效打击）、强制交换（正交相邻可移动格可无匹配交换）、洗牌。各关初始库存写在内容中，无广告/支付前提；取消或无效目标不扣道具。道具和普通消除共享目标/命中记账。它们是可独立验证的内容，不声称价格与库存等同原版。
11. 交换和连锁处理期间锁定新的棋盘动作，明确丢弃且反馈忙碌状态；暂停、退出仍可用。视觉阶段消耗呈现时钟，逻辑结算结果不受帧率影响。关闭动画时，最终状态、得分、RNG 必须一致。**不要求把逻辑运算拆到动画帧中**：可保留同 Tick 原子求解，由共享 Runtime 输出完整有序结算事件与动画计划，再分阶段呈现；也可采用确定性的分阶段逻辑。两种方式都必须由共享会话定义输入屏障/恢复边界，adapter 不得自行接受下一步或决定胜负。
12. 存档在稳定逻辑事务提交点写入；若处理中退出，保存最近提交点以及未显示完的呈现序列或采用明确的恢复到稳定结果策略。恢复不得重扣步数、重复得分、重复发奖。关卡进度取最好结果，失败/重打不会降低旧星级。
13. **默认计分是本次设计值，并非原版实测值。** 每个普通棋子实际清除10分；每个特殊棋子实际消费/激活10分，组合的两个参与者各计一次；每削去一个障碍层20分；每个目标收集物成功到出口50分。转化/新生成特殊块、下落、补充、交换本身、洗牌、目标完成附加奖励均为0分；连锁波倍率固定1，剩余步数奖励默认0。一次结算增量为 `10×被清除普通棋子数 + 10×被消费特殊棋子数 + 20×削去障碍层数 + 50×出口收集物数`；四项用互不重复的实体/事件记账，收集物不再额外按普通棋子计分，正常棋子与其底层障碍可以各计一次。道具导致的清除使用同一公式。所有分数都是非负整数，最终结算不加未声明的奖励。
14. **星级也是本次设计合同。** 每关在JSON公开正整数 `baseScore=B`，星级展示门槛为 `[B, ceil(1.5×B), 2×B]`。必须先通过MR08确认所有目标完成：失败或未完成为0星，不解锁下一关，即便分数已超过三星门槛。成功局至少1星；成功且 `score >= ceil(1.5×B)` 为2星，成功且 `score >= 2×B` 为3星；成功但低于B仍为1星。比较使用 `>=`，恰好门槛晋级、差1分不晋级。B是公开难度/评分参数，不构成隐含通关目标，若某关需要分数目标必须另列。实际关卡交付时要提供合法输入见证证明其公布的高星门槛可达；本设计未提供棋盘或见证，因此**不预先宣称12关均能三星**。不可达时应调整关卡或公开阈值后再冻结，不通过发放隐藏分数补救。

### 6. 验收设计与证据

本包测试目录中的 M3-01–20 提供20条用例，全部 `NOT_RUN`。夹具名称为将来交付义务，本轮没有生成实际棋盘、求解见证或执行日志。

独立 Agent 应从公开 Manifest/能力说明、作品规则和素材目录生成一个未看过的关卡变体，仅修改 JSON/资源引用，使用同一 Runtime 完成验收。不能以复制固定棋盘、硬编码胜利序列或新增按 gameId 分支的游戏代码证明通用性。

#### 不可合并为一个“PASS”的事项

- 12关与变体可解性见证通过，只证明给定内容和随机策略下存在通关路径；不证明任意玩家局面都有解，也不证明所有随机种子都能通关。
- 无合法步检测证明是否有下一步；目标可达性需独立通关见证，二者不能混用。
- 能创建特殊块的最小夹具通过，不等于完整关卡里玩家真的能形成它。
- Headless 完整结果正确，不等于动画/音效/触控正确。
- 原版精确规则仍有待冻结项时，可称参考作品功能验收完成，不能宣称“原版完全一致”。
- 默认计分和星级公式只使本次验收可精确判断；这些设计值不构成原版数值证据。高星阈值可达性必须随每个实际关卡交付证明。
