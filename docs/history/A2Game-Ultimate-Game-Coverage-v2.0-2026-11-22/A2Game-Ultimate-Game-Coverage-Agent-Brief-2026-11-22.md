# A2Game Ultimate Game Coverage — Agent启动任务

截至 2026-11-22，v2 已完成第 1 至 10 批的作者工程交付，累计 25 款可玩原型。第 10 批的 G156、G122、G107 均通过双 SDK 工程验证和独立接收端导入复验。第 11 批 H09 塔防物流供给已完成工程交付，累计 26 款。第 12 至 40 批按下方优先队列推进。独立 G3、人工质量及适用真机仍按各自条件验收。[试玩指南](../../../games/coverage-v2/README.md) · [项目台账](../../../project/status.json)

本任务把 v2 覆盖目标分成两条交付线。**新增游戏类型**验证一套新的核心循环能完整运行。**已有类型新增玩法**从已有作品出发，增加可实际操作的新机制或策略选择。单纯新增关卡、波次、素材或数值难度记作内容扩充。

规划快照为 `13c64dc07c0e6dde3816f100216bad9565bb1ed0`。实施以当前工作区为基线，开始时记录 HEAD、相关未提交改动与现行功能收口状态。主播放器和独立 SDK 已通过 `RenderSetup` 初始化引擎，通过 `PresentationFrame` 绘制。GameSpec 校验、状态绑定、输入和玩法继续由共享层负责。功能收口与已知问题优先，开发只跑受影响的必要验证，集中回归和正式验收后续单独推进。[项目计划](../../../PROJECT-PLAN.md) · [当前进展](../../../PROJECT-STATUS.md) · [项目台账](../../../project/status.json) · [Player SDK](../../../packages/player-sdk/README.md)

## 阶段 1 · 目标登记与能力核对

1. 以随附目标目录为 v2 登记来源，核对 G01–G192 和 H01–H32 的编号、唯一性、分类与核心循环字段。224 项含已有冻结的 32+5 项及新增的 160+27 项。新增提案独立登记，沿用原 G01–G32、H01–H05 的身份、正式分母和历史证据。GameSpec / Capability Protocol 继续使用 `0.1.0`。[目标总纲](A2Game-Ultimate-Game-Coverage-v2.0-2026-11-22.md) · [目标目录](A2Game-Ultimate-Target-Catalog-v2.0-2026-11-22.json) · [原覆盖登记](../../../specs/v0.1/coverage/games.json)
2. 对新增目标做初筛，为首批候选逐项核对必需机制。当前可从 128 份 Manifest、共享可信绑定和已运行 GameSpec 查证，按「可直接复用」「支持其中一部分」「缺失」「待核实」记录，并附实际 Capability ID、版本、源码或可执行样例。目录里的概念名称仅用于查找。新增类型记录核心循环，已有类型扩展同时记录基线游戏 ID、版本和可观察的玩法增量。[共享可信绑定](../../../src/trusted-modules.ts) · [能力查询](../../../generator/README.md#L78)
3. 首轮交付独立的 v2 目标登记与首批能力映射，列明候选、可复用能力和阻塞。该阶段仅做盘点与登记，运行时代码、模型路由和发布权限保持现状。

首批按两条交付线各选一项。完成能力核对后再确定是直接编写 GameSpec，还是先补共享能力。后续每批最多选 3 项。

1. 优先用已有能力编写 `game.json`，沿用现有 CLI 或 MCP 做完整 Schema、能力和语义准入，以及 Conformance。确有共性缺口时，在共享 Runtime 实现通用 Capability，按项目要求同步 Manifest、绑定、Schema/语义检查、正反例及 Host 支持。Adapter 按通用渲染接口消费表现数据，禁止按游戏 ID 实现玩法。根据实际创作阻塞补充 Skill 说明。[Capability 交付要求](../../../PROJECT-PLAN.md) · [GameSpec](../../../specs/v0.1/docs/01-GameSpec-V0.1.md) · [CLI 用法](../../../generator/README.md)
2. 每款复用现有验证链，至少跑通一条成功路径和一个关键失败或非法操作场景。在目标 Host 实际玩完一局，确认输入、画面、结果及重开和释放。新增跨 Host 共享机制或改变表现接口时，用同一份定义对照真实 Three.js 与 CocosAirJS，核对关键结果和状态 Hash。验证范围按影响确定，保留失败和复跑证据。
3. 交付记录包含目标 ID、工作区基线、玩法增量、能力 ID 与版本、可玩包或作品入口、宿主/SDK 及回执。分别登记能力支持、工程可玩、Agent 创作、Agent 质量和正式验收。当前新增真实模型调用预算为 0，开发者可先编写并验证作品。正式 G3、适用真机和质量验收按各自条件执行。提交、推送、部署、发布权限与凭据操作沿用现有授权边界。

交付时列出本批完成项、未验证或受阻项，以及两条线的下一批候选。
