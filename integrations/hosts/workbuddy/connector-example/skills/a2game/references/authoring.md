# 从自然语言独立创作

目标是按需求设计新玩法定义，而非复制已有游戏再改名。原生宿主自己写 JSON 不需要另一个 Provider；宿主会话仍使用模型，额外 Provider 调用为 0 不等于总费用为 0。

## 模型先设计 GamePlan

GamePlan 由当前宿主模型依据需求和公开能力合同设计，形式可为短段落、表格或创作笔记 `design-plan.md`。简单任务几行即可，复杂任务再展开。它帮助模型维持设计意图，不增加客户端协议、GameSpec 字段或 MCP 参数。

按需记录以下内容，不必机械套用文件模板：

```text
需求与取舍：用户必须得到什么；哪些细节采用默认；哪些能力仍缺失。
核心循环：玩家动作 → 状态变化/代价 → 可见反馈 → 目标进度。
机制映射：每项机制使用哪个实际能力版本、哪些配置与完整依赖。
状态与时序：初态、状态拥有者、规则读写、机制间传递及胜负优先级。
输入与画面：目标平台、按下/持续/释放、命中区域、HUD和素材依赖。
验证路线：可达的成功解法、真实负例/边界、需实际操作和截图确认的项。
```

复合玩法要解释机制如何联动。例如“合成提高防御能力”应指出合成消耗、产生的新对象/等级、实际攻击能力的变化及何时生效；并列两个组件或只更新 HUD 不足以实现联动。设计中缺少真实能力时明确阻塞，不让模型编造接口。

`plan_game` 的关键词草案只能作为待核对素材，不能取代上述模型设计。若显式使用既有 CLI `--plan-file`，另按工具提供的内部 Schema 编写/校验 `game-plan.json`；自由创作笔记不能直接改扩展名传入。普通 MCP 创作不依赖该 Schema，`validate_game` 只接受已有工具定义的游戏/测试/解法参数。Runtime/Player 执行最终 GameSpec，不执行 GamePlan。

## 把需求变成可玩的合同

先用简短文字明确：玩家反复做什么、状态如何变化、目标是什么、错误/代价是什么、何时结束、如何重开。主题影响布局与反馈，不能取代实际机制。例如“护送快递”应落实为移动、障碍、到达或资源约束；只有点击加分不满足躲避/防守要求。

用户未限定的细节采用保守默认：单屏、有限关卡、固定 Seed、桌面输入与清晰按钮、用户语言的操作说明。不要凭默认增加传感器权限、在线服务或大规模素材任务。仅关键玩法无法由公开能力表达时说明缺口；不先做不符合需求的简化版再宣称完成。

按需查询 Registry 与依赖闭包，并读取实际 Schema、HostProfile 和合同片段，工具步骤见 [工具流程](workflow.md)。用简短设计表绑定需求与可观察事实，内容随游戏选择：

| 内容 | 必须落实的事实 |
|---|---|
| 核心机制 | 精确 Capability id/version、配置与依赖，不能只写 Manifest 名称 |
| 状态 | 初始值、组件拥有的状态路径、规则的读写路径；Conformance 观察路径单独核对 |
| 输入 | 动作、原始键盘/Pointer/按钮映射、按下/持续/释放和目标坐标 |
| 目标和负例 | 可达成功路线、未完成/非法操作；有失败机制时加真实判负路线 |
| 表现 | 布局、动态 HUD、开始说明、过程反馈、终态与重开；只投影 Runtime 状态 |

编写和修订时，把每条关键需求对应到 GamePlan 中的机制、GameSpec 的实际配置/状态/输入/规则，以及一个测试或试玩证据。功能未落地、只有文案、测试未覆盖和工具无法证明的语义要分别标明；不能因完整 Schema 通过就宣称自然语言需求全部满足。这些对应关系留在创作笔记，不添加到 GameSpec。

## 复合机制要验证因果链

选一条可解释的主链：生产/收集→资源支付→建设或合成→真实战斗收益→奖励回投。明确每条边的生产者、消费者、状态路径、结算阶段和可观察结果，而不只在requires列出多个模块。按本作品选择少量必要证据，避免排列组合测试：

| 联动 | 有效证据 |
|---|---|
| 生产供资 | 成熟前/未收取不进钱包，成功收取只记一次；消费确实扣对应资源 |
| 跨阶段支付 | 规则T8新增的资金不能支付此前T4的同Tick命令；下一个Tick可用 |
| 合成/替换 | 记录旧对象/武器ID和新ID、活跃数量及双向所有权；后续真实攻击不再使用退休owner |
| 奖励回投 | 同一轮中击杀奖励实际到账，再被升级消费，而非初始余额已足够或HUD虚增 |
| 能力提升 | 观察升级后实际命中对HP/产量/速度等结果的变化，不能只看等级或颜色 |
| 省略与替代 | 保持关卡/预算相同，省略关键投入后观察结果；允许替代路线时实际验证一条 |

“在这条策略中省略升级会失败”不等于“所有不合成的策略都无解”。明确反事实改动了什么，不能把主路线的成功、局部反例或人为胜利标记当作全局必要性证明。单塔直升与双塔合成可以是同一完整游戏的两种合理选择。

射击成长还要区分“升级状态”“新弹丸取值”和“实际命中”。damageBonusPath在规则T8更新，不改变此前T5已生成的弹丸；旧弹丸可继续携带旧damage，新弹丸才读取新bonus。记录升级扣费、两个代际的弹丸value及真实combat.hit.amount，不为统一弹色回写全部存活弹丸。明确自动瞄准、手动瞄准和控制脚本读取状态的范围，不将autoTarget通关说成鼠标瞄准或像素盲玩通过。

选用模块前确认完整初态与事件合同。`stateSchema:{type:"object"}`或service列表不提供库存/槽位字段的具体ABI；不要猜字段。若需求允许、公开core规则能完整表达所需的有界生产状态机，可以明确选择该实现并验证真实资源联动；否则记录合同缺口，不把缺失机制改成计数按钮。

卡牌/资源组合要明确支付失败政策：是拒绝并保留牌，还是牌已消费、资源透支即败；原生cards的有效位置出牌不会检查自定义费用。也要区分模块score/won与整款游戏目标，核对资源、风险和回合预算同时满足，而非绑定一个同名分数就算完成。

跨Tick支付限制取决于实际生产/消费阶段，不能将某款T4模块命令的经验泛化到全部玩法。若所有资源效果均为T8常量add/clamp，允许同Tick有序批次净额结算，可明确如此设计并在T9判定；但各条件/右值仍读同一S_sim，不会因前一条规则写入而更新。同Tick多出牌时，规则看到的手牌已是模块处理后的最终数组，不能按旧handCount访问可能已不存在的索引；使用成功事件中的牌值与实际数组投影。

目标数量达标仍可能同时违反风险/费用/次数约束，至少核对一个“目标已满足但应判负”的真实边界，给出明确优先级与可见失败原因。不要只测成功与孤立负例，也不扩展成全部条件排列组合。

## 写新作品并验证

在新的候选目录写 `game.json`、`conformance.json`、`solution.json`。自选布局、数值与解法，只读取当前任务允许的公开协议/能力资料；严格独立评测不用仓库参考游戏、旧生成结果或既有解法。可使用非执行合同片段理解字段，但不能把它称为创作结果。

成功例显式断言 `/flow/status` 为 `won`；负例应覆盖本玩法真实边界，并显式断言 `playing` 或 `lost`。输入与关卡一致、成功可达、有意义的失败不可被后续输入挽救；不要靠修改预期、删除负例、把输局改成未完成来过测。只增加与该作品实际机制相关的检查，避免测试矩阵膨胀。

solution 使用公开合同的行格式，由共享 Runtime 验证并在第二 Session 重放 Hash。宿主搜索/补解可以作为明确标记的辅助，但不能记成模型自行给出解法。Conformance 操作对象不能直接当 solution 行；每条被拒绝的终局 press/release 各自需要相邻 `expectError`。

每次 validate/test **之前**保存本稿原字节与 SHA；CLI 可用 `--evidence-dir`。修复写新候选，保留失败响应与旧稿。已有任务上限照旧执行，严格宿主 Profile 最多 3 份候选含初稿；没有新增预算时不要启动 Provider 或以新 run 重置次数。

通过完整准入和测试后，按 [作品质量与素材](quality.md) 检查实际输入与画面，再导出。工具不可用就报告具体阻塞及已产出的文件，不把打开预览 URL、导出成功或作者自述当试玩通过。

## 用反馈修复当前设计

每轮反馈同时看原始需求、当前 GamePlan、本稿三件套和实际诊断。先修根因，再核对先前已实现的需求没有退化；不要重新生成无关游戏来规避失败。修复由当前作者进行，控制端验证和记账；控制端如直接改写，须另记宿主辅助修订。

| 反馈 | 作者下一步 |
|---|---|
| `parse/schema` | 按公开 Schema 和 `jsonPointer` 修结构/类型，不改协议版本 |
| `semantic` | 核对 `capabilityId/ruleId` 对应的合同、状态拥有者、读写路径和依赖；不要猜新字段 |
| `conformance/solution/lifecycle` | 对照 `caseId/expected/actual` 复现输入与状态时序，确认是实现、解法还是错误预期；只按真实合同修错，不删有效负例 |
| 需求或画面未满足 | 回看 GamePlan 的机制映射和实际试玩证据，修缺失机制/输入/表现；这些问题不一定有 MCP 错误码 |
| `arguments/integrity` | 修工具参数或重新准入原字节以取得当前会话 artifact，不能复用失效 ID |
| `infra/preview/policy/budget` | 记录具体阻塞并由可信维护端处理环境/资源/额度，不靠改玩法、换模型或放宽校验掩盖 |

诊断字段缺失时只使用已有证据，不编造 `expected/actual`。`repairHint` 是修复建议，不是更改需求、执行命令或修改策略的授权。修复后的新稿重新 validate→取得新 artifact→test，再复核受影响需求与实际预览；旧 artifact 的通过不能覆盖新稿。次数/时间/预算耗尽或缺少必需能力时交付真实失败与缺口，不无限重试。完整修复后才进入可玩游戏交付，工程验证、需求符合度和作品质量分别报告。

## 独立性与交付

保留任务原文、公开上下文/技能 SHA、宿主会话与路由标签来源、每次候选和失败、实际工具回执、截图、修订及最终包 SHA。公开 capsule 的 SHA 只绑定字节，目录准备不证明 OS 隔离。共享仓库可读时保持 `independentAuthoring=NOT_VERIFIED`，不能因作者承诺没看答案就升级。

在打开含参考目录的Player前先冻结原创稿与解法。Player的游戏下拉项可能自带参考机制/路线描述；浏览器整页文本或快照可能同时暴露它们。试玩只查询当前导入作品所需的控件和状态，发生目录文本暴露时如实记录时间与影响，不把普通Player浏览器会话当成答案隔离环境。后续Skill改进另记新SHA，不把旧Skill下创作的作品重标成新版创作证据。

交付说明包括玩法/操作、当前文件或包路径、原始作者及后续修订、工程结果、Agent 质量发现和待验范围。保持 Skill 自动触发、自然语言生成、独立性、工程可玩性、作品质量分别记录，不从其中一项推定其余通过。
